# Reactome Website Constitution

The principles below are not aspirations. Each one is here because breaking it
cost this project something specific, and the cost is named so the rule can be
argued with rather than merely obeyed.

## Core Principles

### I. Verify the instrument before trusting the measurement

A green check, a passing selector or a count proves nothing until you know what
it points at. A link crawl reporting "186 broken links" was our own request burst
tripping rate limiting — 403, not 404. A readiness probe gated on a URL the bot
protection rejects would have skipped its test forever. A scroll measurement read
a 146px container that was not the one on screen. An element count read 0 for a
page that had rendered correctly.

So: name what a measurement is actually reading. When a number is surprising,
suspect the instrument first. Prefer a signal the feature cannot fake — assert
that a panel is _open_, not that it is rendered; assert the selection reached the
URL, not that a button looks pressed.

### II. Measure in the thing, not in your head

Reasoning about behaviour is how you form a hypothesis, never how you confirm
one. Mapping a legacy fragment passed a typecheck and 19 unit tests, then failed
in a browser twice for two different reasons — a query string replaced before it
was read, and a reader that resets any param the URL does not mention. Neither
was visible from the source.

So: for anything a reader can see or a URL can carry, the evidence is the running
app. A change to routing, rendering or state is not done until it has been
observed working end to end.

### III. Prove a test fails before believing it passes

A test written after a fix, and never seen red, describes the fix rather than
guarding it. The guard against `?sample=GC__content` silencing every URL write
was confirmed by restoring the old code and watching the case fail; the
`--no-renames` fix by running the same `git mv` both ways.

So: when a change is a bug fix, show the new test failing against the old
behaviour. When that is impractical, say so in the commit rather than implying
coverage you have not demonstrated.

### IV. The reader is never left holding an unstable identifier

Stable ids (`R-HSA-…`) survive releases; dbIds do not. A dbId in a URL, a link or
a shared address is a link that breaks silently at some future release, with no
error anywhere. This is why 316 links in our own news archive were rewritten, and
why an incoming dbId is resolved and the URL corrected in place.

So: resolve to a stable id and normalise the address. Legacy dbId inputs are
still accepted — citations and bookmarks cannot be edited — but they are never
where a reader is left.

### V. Comments carry the failure, not the mechanism

Code says what it does. A comment earns its place by recording what went wrong
without it, because that is the part the next reader cannot recover. "One frame,
and it has to stay one" beside a scroll restore is what stops someone
"simplifying" the two-frame reveal it depends on. A comment that merely narrates
the line beneath it is noise, and a comment with an unverified number in it is
worse than none — two of ours claimed counts that reproduced at no scope.

So: explain the why and the failure. Any figure in a comment must be one you
measured, and measurable again.

## Quality Gates

Every change passes, locally and in CI:

- `npm test` — unit tests
- `npm run check:types` — `strictTemplates` is on; a silent-render bug cannot land
- `npm run check:lint` — warnings ratcheted against `lint-baseline.json`, never upward
- `npm run check:dead` — unreachable code ratcheted against a baseline
- `npm run format:check` — Prettier
- `npm run e2e` — _is the code right?_ Must not need freshly generated release data
- `npm run e2e:release` — _is the release right?_ Run against the site being released

`scripts/preflight.sh` runs the lot and is wired into the pre-push hook.

Two ratchets, two baselines: a change may lower them and must never raise them.

## Development Workflow

- **`main` is protected.** No direct pushes. Every change is a pull request with
  all six required checks green. Reviews are not required, so the checks are the
  review.
- **Squash merge**, and branches are deleted on merge. Because branch protection
  is `strict`, a PR goes stale the moment another merges — `gh pr update-branch`
  rather than a local rebase. Verify a commit landed by inspecting the _merge
  commit_, never the branch: a commit pushed after auto-merge fires goes nowhere.
- **Never run concurrent git operations** in this repo. A backgrounded commit
  plus a checkout in the same tree loses the commit to a lint-staged git error.
- **Content lives in `.mdx`** under `projects/website-angular/content/`. `cms/*`
  branches are restricted to content and uploads; `content-dist/` is generated by
  `stage:content` and does not belong in a content PR.
- **The curator documents are part of the work.** `RELEASE-TESTING.md` and
  `CURATOR-REPORT.md` are kept current as changes land — every row that becomes a
  test is a row a curator never reads again. Mark items **auto** (a named spec
  asserts it), **human**, **gap** or **missing**, and do not claim **auto**
  without naming the spec.
- **Do not restructure `ngx-reactome-diagram` or the `curator-tool` branch**
  without looping in their owners.

## Governance

This constitution supersedes convention, including this codebase's own existing
patterns: where a touched file follows a legacy approach and current framework
practice differs, prefer current practice and say why.

Amendments are made by pull request, and must state which principle changed and
what it cost to learn. A principle with no cost behind it does not belong here.

Complexity must be justified in the PR that introduces it. Scope stays as asked:
finish the whole request, and raise anything beyond it rather than quietly
building it.

`CLAUDE.md` carries day-to-day development guidance; where the two disagree, this
file wins.
